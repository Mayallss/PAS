## 2. ระบบการลา (`/leave`)

### 2.1 ประเภทและสิทธิ์ (ค่าตั้งต้น — แก้ได้ที่แท็บ “จัดการ (HR)”)

| ประเภท | สิทธิ์/ปี | เงื่อนไข | ที่มา |
|---|---|---|---|
| ลาพักร้อน | 6 วันทำงาน | ทำงานครบ 1 ปี (ปีที่ครบได้เต็ม [ข้อเสนอ]) | [กฎหมาย] ม.30 |
| ลากิจ | 3 วันทำงาน | ได้รับค่าจ้าง | [กฎหมาย] ม.34, ม.57/1 |
| ลาป่วย | 30 วันทำงาน (ที่ได้ค่าจ้าง) | ลาได้เท่าที่ป่วยจริง; ตั้งแต่ 3 วันทำงานขอใบรับรองแพทย์ | [กฎหมาย] ม.32, ม.57 |

- 1 วัน = 540 นาที (9 ชม.) [ผู้ใช้ 2026-09-29]; ปีลา = ปีปฏิทิน [ข้อเสนอ]
- HR เพิ่มประเภทใหม่ได้ (ลาคลอด 98 วัน ม.41, ลาบวช, ลาไม่รับค่าจ้าง …) — ระบบสร้าง Activity การลาในบันทึกเวลาให้เอง
- **ยอดใช้ไป** = ใบลาที่อนุมัติ + รายการลาที่ลงในบันทึกเวลาก่อนมีระบบนี้ (ข้อมูลเดิมปีที่ขึ้นระบบ) ; **คงเหลือ** = สิทธิ์ − ใช้ไป − รออนุมัติ

### 2.2 ขั้นตอน

```
พนักงานยื่น (วันหรือชั่วโมง) ──► หัวหน้าทีม (ไล่ขึ้นตามโครงสร้างทีม) อนุมัติ / ไม่อนุมัติ (ต้องมีเหตุผล)
        │                             ทีมไม่มีหัวหน้า → HR
        └─ HR บันทึกแทน + อนุมัติทันที (ใบลากระดาษ / ป่วยแจ้งทางโทรศัพท์)
อนุมัติ ──► คำนวณวันใหม่ (ตารางงาน/วันหยุดล่าสุด) ──► ลงบันทึกเวลา (แถวลา แก้ไม่ได้) ──► คิวส่ง Google Calendar (Out of office)
```

| กฎ | รายละเอียด |
|---|---|
| นับเฉพาะวันทำงาน | ตามตารางงานของคน (ราย/ทีม/บริษัท) หักวันหยุด; วันหยุดครึ่งวันคิดเฉพาะส่วนที่ต้องทำงาน |
| ห้ามอนุมัติใบของตัวเอง | ทุกคน รวมถึง HR |
| ซ้อนกัน | ประเภทเดียวกันวันเดียวกันไม่ได้; ต่างประเภทได้ถ้ารวมไม่เกินเวลาทำงานของวันนั้น |
| เกินสิทธิ์ | ยื่นได้ แต่ติดป้าย “เกินสิทธิ์” ให้ผู้อนุมัติเห็น (ลาป่วยเกิน 30 วันถูกกฎหมาย แต่ไม่ได้ค่าจ้าง) [ข้อเสนอ] |
| ย้อนหลัง | ตามนโยบายบันทึกเวลา (`backdateDays`, ค่าเดิม = ไม่จำกัด); HR บันทึกย้อนหลังได้เสมอ |
| ล่วงหน้า / ช่วงยาว | ไม่เกิน 365 วันล่วงหน้า, ใบละไม่เกิน 120 วันปฏิทิน [ข้อเสนอ] |
| งวดปิดแล้ว | ยื่น/อนุมัติ/ยกเลิกในเดือนที่ปิดงวดไม่ได้ |
| ยกเลิก | ผู้ลา: ใบรออนุมัติได้เสมอ, ใบอนุมัติแล้วก่อนวันเริ่ม; HR: ทุกใบ → แถวลาในบันทึกเวลาถูกลบออก |
| ความเป็นส่วนตัว | เหตุผลการลาเห็นเฉพาะผู้ลา หัวหน้า HR; ปฏิทินทีมแสดงแค่ “ลา” ไม่บอกประเภท (ลาป่วย = ข้อมูลสุขภาพ PDPA) |
| บันทึกเวลา | แถวลาแก้/ลบไม่ได้, กรอกเวลาบน Activity ลาด้วยมือไม่ได้ (ให้ยื่นใบลา) |

## 3. จองห้องประชุม (`/rooms`)

| แบบ | ห้อง | ลิงก์ |
|---|---|---|
| ที่บริษัท | ต้องเลือก | — |
| ออนไลน์ | ไม่ใช้ห้อง | พิมพ์เองได้ หรือ Google Meet สร้างให้เมื่อเชื่อม Google |
| ที่บริษัท + ออนไลน์ | ต้องเลือก | เช่นเดียวกัน |

- ตารางรายวัน (ห้อง × 08:00–19:00) คลิกช่องว่างเพื่อจอง, รายการ “การประชุมของฉัน”, เชิญเพื่อนร่วมงานและแขกภายนอก (อีเมล)
- **จองซ้อนไม่ได้** — ตรวจก่อนบันทึก + DB exclusion constraint (`room_booking_no_overlap`), ต่อเวลากัน (10–11, 11–12) ได้
- กฎ [ข้อเสนอ]: ทีละ 5 นาที, 15 นาที–12 ชม., ล่วงหน้าไม่เกิน 180 วัน, จองย้อนหลังไม่ได้, ผู้จองหรือ `room.manage` แก้/ยกเลิกได้, จบแล้วแก้ไม่ได้
- ห้อง: ชื่อ ตำแหน่ง ความจุ (เตือนเมื่อคนเกิน) อุปกรณ์ สี และ **อีเมลห้องใน Google Workspace**
- ช่อง `meeting_id` เตรียมผูกการจองกับรายงานการประชุม (ยังไม่มีหน้าจอ)

## 4. Google Calendar — เขียนไว้แล้ว รอเปิด

### 4.1 ทำงานอย่างไร
- ทุกการเปลี่ยนแปลง (จอง/แก้/ยกเลิก, อนุมัติ/ยกเลิกใบลา) บันทึกในตาราง `calendar_sync` (outbox) ใน transaction เดียวกัน
- Worker ทุก 1 นาที ส่ง **สถานะล่าสุด** ไป Google: สร้าง / แก้ / ลบ — ลองซ้ำแบบ backoff สูงสุด 8 ครั้ง, หลาย instance ไม่ส่งซ้ำ
- ยังไม่ตั้งค่า → รายการรอ (PENDING) ไว้ และถูกส่งเมื่อเชื่อม (เฉพาะที่ยังไม่ผ่านไป)
- การจอง → นัดในปฏิทิน **ผู้จอง** (ส่งคำเชิญผู้เข้าร่วม+แขก, จองห้อง Google, ลงปฏิทินบริษัท, เตือนบนมือถือ 1 วัน + 30 นาที, สร้าง Meet ให้แบบออนไลน์แล้วแสดงลิงก์ในพอร์ทัล)
- ใบลาเต็มวันที่อนุมัติ → **Out of office** ในปฏิทินผู้ลา (Google ปฏิเสธนัดใหม่ช่วงนั้นให้, ไม่บอกประเภทการลา); ลาเป็นชั่วโมงไม่ส่ง (ไม่มีเวลาเริ่ม)

### 4.2 ขั้นตอนเปิดใช้ (เมื่อมี Workspace)
1. Admin console → Buildings and resources → สร้างห้องประชุม → คัดลอกอีเมลห้อง (`…@resource.calendar.google.com`) ใส่ในพอร์ทัล (จัดการห้อง)
2. สร้างปฏิทินกลาง “ปฏิทินบริษัท” → แชร์ให้ทุกคน → Calendar ID ใส่ `GOOGLE_COMPANY_CALENDAR_ID`
3. Google Cloud → เปิด Google Calendar API → สร้าง Service Account + key → `GOOGLE_SA_EMAIL`, `GOOGLE_SA_PRIVATE_KEY` (เก็บใน Secret Manager)
4. Admin console → Security → API controls → **Domain-wide delegation** → Client ID ของ Service Account + scope `https://www.googleapis.com/auth/calendar`
5. อีเมลพนักงานในพอร์ทัลต้องตรงกับบัญชี Workspace
6. รีสตาร์ท API → หน้า “จองห้องประชุม” / “การลา (HR)” การ์ด Google Calendar ต้องขึ้น “เชื่อมต่อแล้ว” → กด “ส่งตอนนี้”

⚠️ Domain-wide delegation ให้ Service Account เขียนปฏิทินของทุกคนได้ — จำกัด scope เฉพาะ calendar, เก็บ key ใน Secret Manager, หมุน key เป็นระยะ

## 6. หลักการ: ส่วนเสริมล้ม ระบบหลักต้องไม่ล้ม [ผู้ใช้ 2026-10-02]

> “ถ้าไม่ได้เชื่อม Google ก็ใช้ … ได้ คืออะไรไม่ได้ก็แค่ไม่ได้เป็นส่วนเท่านั้น ห้ามพังทั้งระบบ”

| ส่วนเสริม | ไม่ได้เชื่อม / มีปัญหา | ยังใช้ได้ |
|---|---|---|
| Google Calendar | ไม่มีนัดในปฏิทิน Google / แจ้งเตือนบนมือถือ — รายการรอคิว ส่งเองเมื่อเชื่อม | จองห้อง, ยื่น/อนุมัติลา, แผนงาน, บันทึกเวลา บนเว็บครบ |
| Google Login (SSO) | ล็อกอินใหม่ด้วย Google ไม่ได้ → หน้าเข้าสู่ระบบแจ้งชัดเจน (ไม่ใช่ error 500); ลองใหม่ได้ทันทีเมื่อ Google กลับมา (เดิมค้างจนรีสตาร์ท) | ผู้ที่เข้าระบบอยู่แล้วใช้งานต่อได้ (session เป็นของเรา) |
| monday | เมนูรับ–ส่งเอกสารแสดง “ยังไม่ได้เชื่อม” | ทุกเมนูอื่น |

กลไกที่ทำแล้ว
- **ค่าตั้งค่าส่วนเสริมผิด ≠ เซิร์ฟเวอร์ไม่ขึ้น** — ค่าของ Google/monday ที่ผิดถูกปิดเฉพาะส่วนนั้น + แจ้งเหตุผล; key ของ Google ถูกตรวจตอนเริ่ม (อ่านไม่ได้ = ปิด Calendar); ค่าหลัก (ฐานข้อมูล ฯลฯ) ยังเข้มงวด (`config.ts`, `config.spec.ts`)
- **หน้าแรก/กระดิ่งแจ้งเตือนแยกส่วน** — ส่วนไหนโหลดไม่ได้ถูกตัดออกและบันทึก log ส่วนอื่นยังแสดง (`home.service.ts` `soft()`, `resilience.spec.ts`)
- **หน้าเว็บ** — วิดเจ็ตเสริม (กระดิ่ง, การ์ด Google Calendar) ห่อด้วย `<Optional>` พังแล้วหายเฉพาะตัว; กระดิ่งรองรับรายการชนิดใหม่ที่เว็บยังไม่รู้จัก
- **บอกผู้ใช้ตรง ๆ** — `GET /api/integrations` + แถบบอก “ยังไม่ได้เชื่อม… — ยังใช้ X ได้ ขาด Y” ในหน้าที่เกี่ยวข้อง; หน้า Admin “การเชื่อมต่อระบบภายนอก”
- **Google Calendar sync** — outbox + retry/backoff; ล้มเหลวไม่กระทบการจอง/การลา

กฎสำหรับโมดูลใหม่: ส่วนเสริมทุกตัวต้อง (1) มีสถานะใน `/api/integrations` (2) ปิดได้โดยระบบหลักไม่เปลี่ยน (3) ไม่ถูกเรียกในเส้นทางหลักแบบ synchronous — ใช้ outbox/คิว (4) มีเทสต์กรณี “ไม่ได้เชื่อม”

| รหัสผ่านเดิม (MD5) | **ไม่ย้าย** — ทุกคนตั้งใหม่ |
| การตั้งรหัสครั้งแรก / ลืมรหัส | Admin กด “สร้างลิงก์ตั้งรหัสผ่าน” ในหน้าพนักงาน → ลิงก์ + QR ใช้ครั้งเดียว 72 ชม. → พนักงานตั้งเอง → เข้าระบบทันที; Admin ไม่เห็นรหัส; เก็บเฉพาะ hash ของ token |
| การเก็บ | scrypt (N=2^16, r=8, p=2 — OWASP) ในตาราง `local_credential` แยกจากข้อมูลพนักงาน; พารามิเตอร์อยู่ใน hash เพิ่มความแข็งได้ภายหลัง |
| นโยบายรหัส | ≥ 10 ตัวอักษร (NIST: ความยาวสำคัญกว่าความซับซ้อน), ไม่มีชื่อผู้ใช้อยู่ในรหัส, ไม่ใช่รหัสยอดนิยม — ประโยคภาษาไทยได้ |
| เดารหัส | ผิด 5 ครั้ง → ล็อก 15 นาที (Admin ปลดได้); จำกัด 30 ครั้ง/นาที/IP; ข้อความผิดเหมือนกันทั้งชื่อผู้ใช้ผิดและรหัสผิด (เวลาตอบเท่ากัน) |
| เปลี่ยนรหัส | เมนูไอคอนกุญแจข้างชื่อ → `/account`; เปลี่ยนแล้วเครื่องอื่นออกจากระบบ |
| ลาออก / ปิดบัญชี | พนักงาน INACTIVE เข้าไม่ได้ทันที; Admin ลบการเข้าด้วยรหัสได้ (ตัด session ทั้งหมด) |
| ทุกเหตุการณ์ | บันทึก audit: login สำเร็จ/ล้มเหลว, สร้างลิงก์, ตั้ง/เปลี่ยนรหัส, ปลดล็อก, ลบ |

ขั้นตอนเปิดใช้จริง: นำเข้าคน → (ตัดสินใจ) → Admin สร้างลิงก์ทีละคน ส่งให้เจ้าตัว (ไม่ส่งในกลุ่มแชต) — ถ้าต้องการพิมพ์ QR ทั้งบริษัทครั้งเดียว ทำเพิ่มได้
